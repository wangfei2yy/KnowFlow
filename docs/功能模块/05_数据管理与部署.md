# 模块 05 · 数据管理与部署

> 本地优先的持久化方案、备份恢复、隐私安全与发布部署。
> 返回主文档：[项目说明文档](../项目说明文档.md)

---

## 一、本地持久化

- 数据存于浏览器 **IndexedDB**（Dexie.js），刷新、关闭浏览器均不丢失
- 主键 UUID，时间统一 ISO 8601
- 表结构：`documents` / `categories` / `tasks` / `flashcards` / `aiJobs`（见主文档「数据模型」）
- Schema 版本管理：Dexie `version(N)` 声明式升级（当前 version 2，flashcards 表含 createdAt 索引支持排序），升级自动迁移，无需手动清理数据
- 小知的好感度与对话记录存于 localStorage（轻量状态与本地库分离）

## 二、备份与恢复

- **JSON 导出**：全部资料、分类、任务、卡片一键导出为 JSON 文件
- **JSON 导入**：支持 **合并**（与现有数据共存）与 **覆盖**（清空后导入）两种模式
- 导入前展示数据概览供确认

## 三、清除数据

「设置 → 数据管理」按**类别**清除。分组从 4 个长到 10 个之后，一行一条全铺开会把设置页
撑成一长条，所以分组之上加了一层**分区**：页面按分区折叠，默认只展开「我的内容」。

| 分区 | 分组 | 清掉什么 | 存储位置 |
| --- | --- | --- | --- |
| **我的内容** | 资料与分类 | 资料、分类（卡片不会跟着删） | `documents` / `categories` |
| | 卡片与复习进度 | 卡片、掌握度、下次复习时间 | `flashcards` |
| | 任务清单 | 全部任务 | `tasks` |
| **学习记录** | 闯关与复习位置 | 闯关存档与成绩、复习到第几张 | `localStorage` 三个键 |
| | 背单词进度 | 各词库关卡成绩、未做完的那一关 | `localStorage` 两个键 |
| | 小游戏成绩 | 球球 / 跑酷 / 配对等最高分与局数 | `knowflow.game.progress` |
| | 成语掌握度 | 会 / 模糊 / 不会、错词次数 | 两个键 |
| | 购物清单与计划锁定 | 勾选状态、锁定的菜 | 两个键 |
| **偏好与设置** | 外观与偏好 | 主题、陪伴设置、上次选的词库 | 四个键 |
| | AI 配置与记录 | 模型配置、密钥、AI 任务记录 | `aiJobs` + 六个键（端内不显示） |

### 3.1 为什么要折叠

- **一眼有概览**：顶部先给「共 N 项本地记录 / x 类有数据」，再用一条三色分段条按分区占比画出来，
  不用挨个看就能判断「数据都堆在哪」。没有数据时不画空条，只留一句说明。
- **分区可扩展**：新增分组只要在 `DATA_GROUPS` 里填一个 `section` 字段，自动落到对应分区，
  设置页模板不用改 —— 这是为「以后要管的东西只会更多」留的口子。
- **噪音更少**：空分组不显示「清除」按钮（旧版是置灰按钮，十个灰色按钮反而更乱）；
  内置内容的八类说明默认收成一行，点开才展开。
- 分区聚合逻辑在 `buildSectionViews()` 里，页面只渲染结果，不再自己算百分比。

**内置内容不在此列**（初中/四级/六级词库、语法、成语、食谱、食材）：它们是打包进应用的
静态 JSON，不占本地存储、也删不掉。设置页把它们收成一行可展开的说明 ——
想清掉它们留下的学习痕迹，用「学习记录」分区里的对应类别。

**全部清除**：走同一套分组，并兜底扫掉所有 `knowflow.*` 键。这一点很关键 ——
早期版本只清了 IndexedDB 五张表，闯关存档、背单词进度、游戏成绩全留着，
用户会以为「没删干净」。

清完之后 `localStorage` 里不该剩任何 `knowflow.*` 键，`test:cleanup` 有一条断言专门守这个
（它会检查「代码里用到的所有键是否都登记进了分组」，防止以后新增键漏登记；
同时检查每个分组的 `section` 是否都在分区表里，防止分组成了孤儿不显示）。

> 删除不可恢复，页面顶部保留「导出备份」入口。分组清除用 `ConfirmDialog` 二次确认，标题带分组名。

### 3.2 小知也能清理（机器人侧）

数据管理同时接进了陪伴机器人小知的工具链，两个纯本地工具（不耗 AI 额度、演示模式可用）：

| tool | 触发示例 | 行为 |
| --- | --- | --- |
| `storage` | 「我本地存了多少数据」「缓存占多少」 | 按分区列出有数据的分类与条数，并提示「想清哪一类直接说」 |
| `cleanup` | 「把小游戏成绩清掉」「清空所有学习记录」 | **不直接删**：先回一条确认清单，用户回「确认」才执行 |

- 范围解析（`services/companion/dataTools.ts`）：分组 id / `section:learning`（整个分区）/ `all` 三档。
  先用关键词表匹配具体分组（「小游戏成绩」「背单词」「成语」…），再匹配分区级说法，
  最后才落到全清 —— 否则「清除所有游戏成绩」里的「所有」会误判成全清。
- **必须二次确认**：待确认状态存在内存里（2 分钟过期），只认「确认 / 确定 / 好 / 嗯」这类明确短词；
  用户说别的就作废，绝不因为一句话就删数据。「算了 / 取消 / 不用了」直接放弃。
- 执行后同步刷新资料列表，并保留一句「内置词库和食谱都还在」。

## 四、隐私与安全

| 原则 | 落地方式 |
| --- | --- |
| 本地存储 | 资料默认保存在浏览器 IndexedDB，不上传服务器 |
| AI 授权 | 调用 AI 前告知将发送的内容，需用户主动操作 |
| 密钥保护 | 后端代理模式 Key 仅存服务端 `.env`；BYOK 模式 Key 只存用户本机浏览器 |
| 内容安全 | 用户输入按普通文本渲染，不执行资料中的 HTML/脚本 |
| 诚实声明 | 本地存储不等于加密保险箱，产品不承诺绝对安全 |

## 五、发布与部署

前端为**纯静态应用**：

1. `npm run build` 产出 `dist/`；
2. 部署到任意静态托管（WorkBuddy 发布、Vercel、Netlify、GitHub Pages 等）；
3. 已使用 **hash 路由 + 相对路径**，可部署到任意子路径，刷新不 404。

> 注意：更新部署后浏览器可能缓存旧 chunk，导致点击页面报「Failed to fetch dynamically imported module」，强刷（Ctrl+F5）即可解决。

### 5.1 必须用生产构建启动（踩过的坑）

WorkBuddy 发布默认会用 `npm run dev` 起 Vite dev server。**dev 模式上线是致命的**：
每个模块单独请求、按需转译、不打包不压缩，首屏要发几十上百个请求，词库 JSON 500 KB
也是原样传输。曾经的线上就踩了这个坑，表现为「点开要等好几秒」。

判断方法（一条命令）：

```bash
curl -s "https://<域名>/?sharecode=xxx" | grep -c "vite/client"   # 输出 1 = 还是 dev server
```

正确做法是部署时显式指定启动命令：

```bash
# 平台参数 startCmd
npm run serve:prod      # = vite build && node server.mjs
```

`server.mjs` 是只用 Node 内置模块写的静态服务器（不引入 express 等依赖）：

| 能力 | 说明 |
| --- | --- |
| br / gzip 预压缩 | 只压 >1 KB 的文本资源，结果按「路径 + mtime + 编码」缓存，不重复压 |
| 缓存头 | `/assets/*`（带内容哈希）→ 一年 immutable；`index.html` 与 `sw.js` → no-cache；`/packs/*.json` → 10 分钟 |
| 缺失资源 | `/assets/*` 不存在时返回 404，**不回退 HTML** —— 否则浏览器把 HTML 当 JS 解析，真实错误被掩盖 |
| 安全 | 路径穿越防护、`X-Content-Type-Options: nosniff`、只接受 GET/HEAD |
| 退出 | 监听 SIGTERM 后关闭连接再退出，避免平台重启时端口占用 |

### 5.2 首屏优化记录（2026-10-29）

实测口径：线上单次请求 TTFB ≈ 0.45s 是平台代理的固定开销，所以**少一跳比少 8 KB 更值**。

| 项 | 优化前 | 优化后 |
| --- | --- | --- |
| 启动方式 | vite dev（每模块一转译） | 构建产物 + gzip |
| 主包 | 308 KB 未压缩 | 317 KB → br **113 KB** |
| 首屏请求 | 主包 → 首页 chunk → pack 索引（串行） | html → **app.js + css 并行** → pack 索引 |
| 首页 chunk | 独立 3.2 KB，多等一个 RTT | 静态引入，并进主包 |
| 二次访问 | 每次导航都要走网络 | SW stale-while-revalidate，导航与资源全命中缓存 |
| 词库 | 每次进页面都重新拉（cet4 510 KB） | SW 缓存，二次进入 0 请求 |

`sw.js` 的三条策略：

- **页面导航**：先给缓存（秒开），后台拉新版本下次生效 —— 原来是网络优先，每次都要等 0.45s
- **`/assets/*`**：cache-first（文件名带内容哈希，永不过期）
- **`/packs/*.json`**：stale-while-revalidate

两个必须注意的点：只缓存 `res.ok` 的响应（否则 404 会被缓存住）；`caches.match` 一律加
`ignoreSearch`，否则 `?sharecode=` / `?pack=` 会导致永不命中。

### 5.4 缓存与版本治理：为什么「改了没生效」（2026-10-30）

**报障**：手机上资料列表还是满屏黄字、设置页还是老样子、还特别卡；电脑不卡但同样黄字；
百度浏览器一切正常。

**定位**：三个症状指向同一件事 —— 那几台浏览器加载的是**旧构建**。
- 黄字是 10-30 上午修掉的老 bug（当时所有片段都套 `<mark>`，浏览器默认亮黄底）；
- 设置页分区折叠是当天下午才上线的；
- 「特别卡」是首屏优化前的包。
- 百度浏览器对 Service Worker 支持受限 → 走普通网络请求 → 永远拿到新文件，所以它正常。

**根因**：`sw.js` 的页面导航是「缓存优先 + 后台更新」。这个策略二次打开确实秒开，
但发版后用户会一直吃旧 HTML（新构建资源名变了，旧 HTML 仍指向旧文件），
而后台那次 revalidate 在部分浏览器里没能改写缓存 —— 于是「永远旧版本」。

**改法（三层，任一层命中都能自愈）**：

1. **壳的保鲜期**（`sw.js`）：缓存壳 ≤6 小时内直接给（实测二次打开 **84ms**）；
   超过 6 小时才走网络（2.5s 超时回落缓存）。之所以敢放这么长，是因为第 2 条的版本自检
   保证了「壳旧 ≠ 版本旧」——发版后页面会自己发现并刷新。
2. **版本自检**（`src/utils/appUpdate.ts` + 构建产物 `version.json`）：
   页面加载后 `fetch('./version.json', {cache:'no-store'})`，和编译进 JS 的 `__BUILD_ID__` 比对。
   不一致 → 自动注销 SW + 清空 Cache Storage + 带 `_v=` 重载一次（同一版本只刷一次，防循环）。
   **这是唯一能发现「HTML 被缓存顶住」的手段** —— 页面自己看不出自己是旧的，但 version.json 能。
3. **SW 自身更新**：注册时 `updateViaCache: "none"` + 启动时主动 `update()`；
   SW 不拦截自己的 `sw.js` 请求；`controllerchange` 后自动 reload 一次（首次安装不刷）。
   缓存版本号升到 `knowflow-shell-v3`，旧缓存会在 activate 时被删干净。

另外把搜索高亮的配色从 `bg-amber-200/70`（CSS Color 4 的 `/70` 透明度）换成实色
`bg-amber-200` / `dark:bg-amber-700`：老浏览器不支持该语法时 `mark` 会退回默认黄底，
看起来就像「黄字 bug 又回来了」。

设置页底部加了一个「检查更新」按钮（清离线缓存并重载），报障时让用户点一下即可。

补充（同日）：把首屏预取从「load 后立即」推迟到「load 后 1.2s」，弱网下不再和首屏抢带宽。

#### 5.4a 又一起「一直加载」：SW 内部 fetch 递归（Edge 卡死）

报障：电脑默认浏览器（Edge）一直停在「正在打开你的资料库」，Google 正常。

根因：`sw.js` 里用 `fetch(req)` 去拉网络，而 `req` 是 `mode="navigate"` 的**导航请求**。
Service Worker 内部 fetch 一个自己 scope 内的请求，会**再次触发本 SW 的 fetch 事件** →
又走 `resolveNavigation` → 又 `fetch(req)` → 无限递归。Edge 上导航被自己的 SW 卡死，
Google 因为 SW 缓存/时序不同没触发，所以「Edge 卡、Google 正常」。

修法：所有 SW 内部的 `fetch(req)` 一律改成 `fetch(new Request(req.url))` —— 新构造的
Request 默认 `mode="cors"`，不会命中「navigate」分支，也就不会递归。共三处
（壳回填、packs、assets）。同时把 `main.ts` 里「controllerchange 自动 reload + 每次 load
主动 update()」的组合也去掉——那套在 Edge 上同样可能反复触发 reload，回归最朴素的注册，
版本正确性交给 version.json 自检。

回归保护：`test:build` 加断言「sw.js 必须含 new Request(req.url)」，防止改回 `fetch(req)`。

首屏冷启动实测（600ms 往返）：无缓存 **1.4s** 出内容，命中缓存壳 **84ms**。

补充（同日）：把首屏预取从「load 后立即」推迟到「load 后 1.2s」，弱网下不再和首屏抢带宽。
首屏冷启动实测（600ms 往返）：无缓存 **1.4s** 出内容，命中缓存壳 **84ms**。

回归保护：`npm run test:build` 增加 5 条断言 —— `version.json` 存在、`sw.js` 含 `SHELL_MAX_AGE`、
SW 不缓存自己、缓存版本号已升级。

### 5.3 首屏与模块切换优化（2026-10-30）

反馈：「首次加载慢，点其它模块还会卡住」。用带 600ms 延迟的本地服务器 + CDP 计时复现，
基线数据与改法如下（**同样的 600ms 单次往返**，即线上代理的固定开销）：

| 指标 | 优化前 | 优化后 |
| --- | --- | --- |
| 首帧（FCP，能看到东西） | 1440 ms | **680 ms** |
| 首屏出内容（首页标题可交互） | 1424 ms | 1428 ms（持平） |
| 点「资料库」到出内容 | 1885 ms | **28 ms** |
| 点「任务清单」 | 1275 ms | **32 ms** |
| 点「设置」 | 1301 ms | **62 ms** |

四件事，分别解决「白屏久」和「点模块卡」：

1. **入口 CSS 内联**（`kf-inline-entry-css` 插件）：`<link rel="stylesheet">` 是渲染阻塞的，
   以前首帧要等它一个往返（0.6s），骨架屏都被挡住。入口 CSS 只有 8KB，构建后直接写进
   `index.html` 的 `<style>`，首帧立刻可见。页面级 CSS（OrbPage / ConfirmDialog）仍按 chunk 分开。
2. **首屏骨架**（`index.html` 内联样式 + `#app` 占位）：JS 下载解析那 1.4s 里给一个
   「知间 AI + 进度条 + 正在打开你的资料库…」，Vue 挂载时整体替换。白屏 → 有反馈。
3. **空闲预取**（`src/router/prefetch.ts`）：路由是懒加载的，点进去要现下载 chunk ——
   一次往返就是 0.6~1.4s，这就是「卡住」。现在 `load` 之后用 `requestIdleCallback`，
   按 120ms 间隔依次 `import()` 资料库 / 学习 / 任务 / 设置 / 趣味学习 / AI 工作台。
   省流模式与 2G 网络自动跳过，失败静默。
4. **分包 + modulePreload**：`manualChunks` 把 vue / dexie / icons / vendor 拆开，
   `index.html` 里对公共依赖发 `modulepreload`（并行拉，省掉「先下 A 才知道要下 B」的水位线）。
   分包同样是缓存策略：以前改一行文案整个 110KB 入口都要重下，现在框架和库都还在缓存里。

回归保护：`npm run test:build`（新增）会检查产物 —— 入口 CSS 是否内联、有没有骨架、
有没有 modulepreload、vue/dexie/icons 是否独立成 chunk、入口包是否 <200KB 且不含 dev 代码与 pdfjs。

> 还有一处没动：页面导航的 Service Worker 仍是「缓存优先 + 后台更新」。
> 它让二次访问几乎瞬时，但发版后第一次导航拿到的还是旧 HTML（下一次才是新的）。
> 权衡下来保留 —— 换成网络优先等于每次打开都多等一个往返。

若需真实 AI（后端代理模式），需同时部署 FastAPI 后端并配置环境变量。

## 五之二、全局提示条（Toast）

`appStore.showToast(message, type)` 会显示 1.8 秒后自动淡出（`transition 0.2s`）。

早期版本只把 `visible` 置 true、没有定时器，提示会一直挂在屏幕上只能手动点 ×，
表现为「点了加入计划，提示条赖着不走」。现在：

- 定时器存在模块级变量里，**新提示必须清掉旧定时器**，否则旧定时器会把新提示提前关掉
- 需要更久停留（如错误信息）时，直接调 `showToast` 并接受默认时长；
  不要自己写 `setTimeout(hideToast)`，会和内置定时器打架
