## 一、背景

### 1.1 现状

饮食模块已经有三个 Tab：食谱（121 道）、时令（四季蔬果）、计划（一周/四周 + 购物清单）。缺的是**食材本身的知识**：

| 缺什么 | 现状 |
| --- | --- |
| 食材营养 | 完全没有。计划页至今写着「营养合计当前数据未包含」 |
| 功效 / 宜忌 | 完全没有 |
| 食材 → 菜的反查 | 只能从菜看到材料，反过来「买了菠菜还能做什么」查不到 |

词库那边已经跑通了一条完整链路：内置知识包（`public/packs/*.json`）→ 页面浏览 → 一键加入复习 → SRS 调度 → 学习中心提醒。**食材完全套得上**，不需要新造机制。

### 1.2 一个被否掉的方案

初版想法是在学习中心加第 6 个 Tab「饮食学习」。否掉的理由：

| 问题 | 具体 |
| --- | --- |
| Tab 已经满了 | 现有 5 个（概览/复习/语法/成语/游戏）。手机端是靠**隐藏图标、压到 13px 字号**才一屏放下的，第 6 个必然换行或横向滚动 |
| 入口重复 | 侧边栏已有一级入口「饮食」（食谱/时令/计划）。再加「学习-饮食」，用户不知道从哪进 |
| 心智不对 | 「做菜」靠动手，不靠复习。把它塞进复习队列是负担，不是学习 |

结论：**内容归饮食，记忆动作归学习中心**。图鉴里浏览，点「加入复习」后卡片进入同一条 SRS 队列，学习中心照常提醒 —— 一条线打通，且学习中心零改动。

## 二、目标与非目标

**目标**

- 新增「食材图鉴」：120~150 种常见食材，含营养、功效、挑选保存、宜忌
- 每个食材可一键加入复习，复用现有 SRS，不新建机制
- 食材 ↔ 食谱双向反查：详情里看到「哪些菜用得上」，点进去直接开食谱
- 计划页的营养合计从「未包含」变成「已包含（参考值）」

**非目标**

- 不做营养计算器 / 每日摄入达标度（数据精度不够，容易误导）
- 不做医疗建议（合规红线，见 4.4）
- 不做食材图片（第一版用 emoji，`img` 字段先占位）
- 端内（小红书小工具）不提供：饮食模块整体在端内不注册

## 四、数据设计

### 4.1 数据来源与编译

**方案 A：内置参考表**

| 项 | 内容 |
| --- | --- |
| 数值基准 | 《中国食物成分表（第 6 版）》常见食物每 100g 可食部数值，人工整理 |
| 源表位置 | `data/食材/食材营养表.csv`（与 PDF 素材一样放 `data/`，不入库） |
| 编译产物 | `frontend/public/packs/ingredients.json`（**入库**，随静态托管） |
| 编译命令 | `npm run build:food`（并入 `build:packs`） |
| 覆盖范围 | 先做时令表 113 + 食谱材料 104 去重后的蔬果/菌菇/肉蛋/豆类；盐、油、酱油、淀粉、料酒等调味料**不进图鉴**（没有"学习"价值，且有营养表会很怪） |

> 源表不入库是沿用现有约定（`data/` 含版权 PDF，已在 `.gitignore`）。若换机器重建，需带上这份 CSV；
> 只说 JSON 是编译产物、改数据请改 CSV。

### 4.2 条目结构

```ts
export interface IngredientEntry {
  id: string;              // 拼音或英文 slug，用于路由与卡片去重
  name: string;            // 番茄
  alias?: string[];        // ["西红柿"]
  emoji: string;           // 🍅
  category: "vegetable" | "fruit" | "mushroom" | "meat" | "egg" | "bean" | "grain";
  seasons: ("春" | "夏" | "秋" | "冬")[];  // 空数组 = 四季常见，不标「当季」
  /** 每 100g 可食部，缺省表示该成分不显著 */
  nutrition: {
    kcal: number;
    protein?: number;
    carb?: number;
    fat?: number;
    fiber?: number;
    vc?: number;           // 维生素 C，mg
    potassium?: number;    // 钾，mg
    calcium?: number;      // 钙，mg
    iron?: number;         // 铁，mg
    carotene?: number;     // 胡萝卜素，μg
  };
  /** 功效：1~2 句，只写营养学表述（见 4.4） */
  benefit: string;
  /** 挑选与保存：一句话，实用优先 */
  storage: string;
  /** 宜忌：一句话，写"什么人少吃"而不是"治什么病" */
  caution?: string;
}
```

### 4.3 营养字段口径

- 单位统一：能量 kcal、其余 g / mg / μg，**都是每 100g 可食部**
- 只在数值有意义时填（芹菜的铁 0.2mg 就填，番茄的蛋白质 0.9g 也填；没测过的字段留空，**不填 0**）
- 页面统一展示为「每 100g 可食部 · 参考值」，页脚常驻一行免责：**数据为常见品种参考值，不同产地/季节有差异，不作为医疗或膳食处方依据**

### 4.4 功效与宜忌的写法规范（合规红线）

只能写**营养素 + 已知生理功能**，不能写疾病治疗/预防。上线前逐条过一遍。

| ✅ 可以写 | ❌ 不能写 |
| --- | --- |
| 富含维生素 C，参与胶原蛋白合成，有助于维持正常免疫功能 | 多吃能防感冒、抗病毒 |
| 钾含量较高，有助于维持正常血压 | 降血压、治高血压 |
| 膳食纤维丰富，有助于维持正常肠道功能 | 治便秘、排毒、清肠 |
| 胡萝卜素可在体内转化为维生素 A，有助于维持暗视觉 | 保护视力、治近视 |

同理，`caution` 写「草酸偏高，肾结石人群适量」这种**提示**，不写「肾结石不能吃」。

### 4.5 编译脚本

`scripts/build-food-packs.mjs`：

| 步骤 | 说明 |
| --- | --- |
| 读源表 | `data/食材/食材营养表.csv`（UTF-8 with BOM 容错，逗号分隔，`#` 开头为注释行） |
| 补季节 | 用 `seasons.json` 反查：出现在某季蔬菜/水果列表里就继承该季 |
| 校验 | 必填缺失、数值非数字、`benefit` 为空 → 打 warning 并跳过该条，不中断 |
| 输出 | `public/packs/ingredients.json` + 更新 `index.json` 加一条 `{ id: "ingredients", kind: "docs", title: "食材图鉴", count }` |

## 五、页面设计

### 5.1 列表页 `/kitchen/ingredient`

- 顶部：搜索框（名称/别名/功效关键词）、分类 chips（全部/蔬菜/水果/菌菇/肉蛋/豆类/谷物）、「只看当季」开关
- 卡片网格（2 列手机 / 4 列桌面）：emoji + 名称 + `xx kcal` + 当季小标
- 排序：默认按分类再按名称；当季优先排在前面
- 空态：搜索无结果时提示「换个词试试，或到食谱里看看」

### 5.2 详情（弹层，与食谱详情一致）

| 区块 | 内容 |
| --- | --- |
| 头部 | emoji、名称、别名、分类、季节标签 |
| 营养表 | 两列小表（成分 / 每 100g），空字段不显示 |
| 功效 | `benefit` 全文 |
| 挑选与保存 | `storage` |
| 宜忌 | `caution`（有才显示，用琥珀色提示条） |
| 用得上它的菜 | 反查 `recipes.json`，最多 5 个，点一条直接在食谱页打开该菜（`/kitchen?recipe=<id>`） |
| 底部操作 | `加入复习` / `已加入复习` |

### 5.3 食谱页反查（双向）

食谱详情里，材料标签变成可点：点「菠菜」跳到 `/kitchen/ingredient?focus=菠菜` 并直接展开该食材详情。没有对应食材条目时保持纯文本（不报错）。

## 六、学习闭环

### 6.1 加入复习

复用现有桥接，不新建任何调度逻辑：

```ts
// services/quest/wordCards.ts（已存在）
addWordToReview(packId, word, /* wrong */ false)
```

- `packId` 用 `food`，`ensurePackDocument` 增加一条映射：`food → 《食材图鉴（饮食）》`
- 卡片内容：`question = 食材名`，`answer = 营养 + 功效一句话`（≤ 60 字，见 6.2）
- `wrong = false`：主动加入按「新卡」进队，不当作答错（与成语页一致）
- 已存在同 question 的卡片 → 按钮显示「已加入复习」，不重复插入

### 6.2 卡片文案模板

```
番茄
每 100g 约 20 kcal，富含番茄红素与维生素 C；生吃补维 C，熟吃更利于番茄红素吸收。
```

规则：热量打头 → 核心营养素 → 一句吃法建议。由 `benefit` + `nutrition` 拼装，**不额外调 AI**（避免每次加入都要联网）。

### 6.3 学习中心侧

零改动。食材卡与单词卡、成语卡在同一条 SRS 队列里，概览页的「今日待复习」自动包含它们。

## 十、风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 营养数值不准 | 用户按它配餐会出错 | 统一口径「每 100g 可食部 · 参考值」，页脚免责；抽查 20 条对源表；不做「每日摄入达标」这类强结论 |
| 功效写成医疗宣称 | 合规风险 | 4.4 的对照表作为唯一口径；上线前逐条过；出现「治/防/降/抗（病）」字样直接打回 |
| 条目覆盖不全 | 做菜时查不到 | 未收录时材料标签保持纯文本，不报错；图鉴页提供「这个食材还没有条目」的反馈入口（先不做提交，仅提示） |
| emoji 表意不清 | 认不出是什么 | 名称字号大于 emoji；后续换实拍图只替换渲染层 |
| 数据表难维护 | 加一条要改代码 | 源表是 CSV，加行即可重跑脚本，不碰 TS |
| 端内混入 | 包体变大 / 白屏 | 路由不注册 + knowledgePack 替身补方法 |

## 十三、实现偏差说明

| 项 | 计划 | 实际 | 原因 |

| 源表位置 | `data/食材/食材营养表.csv`（不入库） | `frontend/data/food/ingredients.psv`（**入库**） | 这份表是原创整理、不含版权素材，入库才能保证换机器可重建；同时 `|` 分隔避开了中文逗号串列 |

| 材料标签 | 都可点 | 只有图鉴收录的才可点 | 点了没收录的材料会弹空提示，体验差；现在未收录的保持灰色纯文本 |
| 卡片文案 | 未规定 | `每 100g 约 N kcal；{功效}`，≤70 字 | 复习时先看到热量更好记；超长截断避免卡片被撑开 |
| 图片 | `img` 字段占位 | 未加字段，只用 emoji | 没有实拍素材时占位字段只会长期空着；换来图再加也不迟 |
