## 一、项目概述

### 1.1 产品定位

知间 AI 是一个帮助用户把零散资料转化为可检索知识和实际行动的个人资料管理工具。

用户可以保存网页文本、笔记、文档和学习资料，通过搜索快速找到内容，借助 AI 生成摘要、基于原文回答问题、提取待办事项，并将重要内容整理成复习卡片。

产品核心闭环：

① 收集资料

文本、笔记、文件、网页内容

② AI 理解

摘要、关键词、问答、行动提取

③ 检索与复用

全文搜索、来源定位、知识卡片

④ 转化为行动

任务清单、学习复习、导出成果

### 1.2 目标用户与典型场景

| 用户    | 实际问题            | 产品解决方式           |
| ----- | --------------- | ---------------- |
| 学生    | 课件、笔记太多，复习效率低   | 生成摘要、知识卡片、复习题    |
| 职场人   | 会议记录、方案、工作资料分散  | 提取行动项、截止时间与责任人   |
| 程序员   | 技术文档、报错记录难查找    | 保存技术笔记、全文检索、来源问答 |
| 内容创作者 | 灵感、素材和参考资料混乱    | 标签分类、摘要整理、素材复用   |
| 普通用户  | 收藏内容太多，真正需要时找不到 | 统一收集、搜索、分类与导出    |

### 1.3 参赛产品的核心卖点

1. 不只是资料收藏夹：资料可以进一步转化为摘要、任务和学习卡片。
2. AI 回答有出处：优先从用户保存的资料中回答，并展示对应原文片段。
3. 不依赖 AI 也能使用：本地保存、全文搜索、分类、任务管理等基础功能可以独立运行。
4. 体验门槛低：提供内置示例资料，用户进入页面即可体验完整流程。
5. 重视隐私：MVP 默认本地存储，不要求用户先注册或上传个人资料。

## 三、技术架构设计

### 3.1 技术选型

采用前后端分离、基础功能本地运行、AI 能力可插拔的架构。

| 层级     | 技术选型                     | 说明                   |
| ------ | ------------------------ | -------------------- |
| 前端     | Vue 3 + TypeScript       | 组件化开发                |
| 构建工具   | Vite                     | 快速开发与构建              |
| UI     | Tailwind CSS + Lucide 图标 | 统一视觉风格               |
| 状态管理   | Pinia                    | 统一管理页面状态             |
| 路由     | Vue Router               | 页面导航                 |
| 本地数据库  | IndexedDB + Dexie.js     | 持久化保存资料              |
| 文件解析   | PDF.js、浏览器文本读取           | 提取文件文本               |
| AI 服务  | 统一 AI Provider 接口        | 可接入兼容 OpenAI API 的服务 |
| 后端（可选） | FastAPI + Python         | AI 代理、服务端处理、后续云同步    |
| 数据格式   | JSON、Markdown、TXT        | 导入导出                 |

关键设计原则： 首版不强制依赖后端数据库。用户的资料直接存储在浏览器 IndexedDB 中，刷新页面后仍然存在。AI 功能通过独立的服务接口调用，不可用时提供明确提示，而不是影响其他模块。

### 3.3 核心模块边界

- `资料管理模块`：只负责资料 CRUD、分类、标签和收藏。
- `搜索模块`：负责索引构建、匹配、排序与结果高亮。
- `AI 模块`：负责摘要、问答、关键词、行动项及卡片生成。
- `任务模块`：负责待办状态、截止时间和任务来源。
- `文件模块`：负责导入、解析、格式校验和错误提示。
- `数据模块`：负责持久化、迁移、备份与恢复。
- `设置模块`：负责 AI 配置、隐私说明、数据清理和体验模式。

模块间通过明确的 Service 接口交互，禁止将所有业务逻辑塞进单个 Vue 页面组件。

## 五、数据模型设计

使用 IndexedDB 作为首版的持久化存储。所有主键使用 UUID，时间统一保存为 ISO 8601 字符串。

### 5.1 资料表 `documents`

```
interface Document {
  id: string;
  title: string;
  content: string;
  sourceType: "note" | "text" | "file" | "web";
  sourceName?: string;
  categoryId?: string;
  tags: string[];
  summary?: string;
  keywords: string[];
  favorite: boolean;
  createdAt: string;
  updatedAt: string;
  contentHash?: string;
}
```

### 5.2 分类表 `categories`

```
interface Category {
  id: string;
  name: string;
  color?: string;
  sortOrder: number;
  createdAt: string;
}
```

### 5.3 任务表 `tasks`

```
interface Task {
  id: string;
  title: string;
  description?: string;
  sourceDocumentId?: string;
  status: "todo" | "doing" | "done";
  priority: "low" | "medium" | "high";
  dueDate?: string;
  createdAt: string;
  updatedAt: string;
}
```

### 5.4 学习卡片表 `flashcards`

```
interface Flashcard {
  id: string;
  documentId: string;
  question: string;
  answer: string;
  mastery: 0 | 1 | 2;
  reviewCount: number;
  nextReviewAt?: string;
  createdAt: string;
}
```

### 5.5 AI 处理记录 `ai_jobs`

```
interface AIJob {
  id: string;
  documentId?: string;
  type: "summary" | "qa" | "actions" | "flashcards";
  status: "pending" | "running" | "success" | "failed";
  result?: unknown;
  errorMessage?: string;
  createdAt: string;
  completedAt?: string;
}
```

### 5.6 数据关系

- 一个分类可以包含多份资料。
- 一份资料可以关联多个任务和多张学习卡片。
- AI 处理记录必须能够追溯输入资料和执行状态。
- 删除资料时，对关联任务应提供「保留任务」或「一并删除」选项。
- 导入时校验 ID 冲突、字段类型和数据版本，不能直接无条件覆盖现有数据。

建议使用 Dexie 定义表结构和索引，并提供 `schemaVersion` 版本迁移机制。

## 六、核心业务流程

### 6.1 新增与整理资料


flowchart TD
    A["用户输入标题和正文"] --> B["校验内容"]
    B --> C{"内容有效？"}
    C -- 否 --> D["提示补充内容"]
    C -- 是 --> E["生成 UUID"]
    E --> F["保存至 IndexedDB"]
    F --> G["更新搜索索引"]
    G --> H["刷新列表和统计"]
    H --> I["提示保存成功"]


实现要求：

- 标题必填，正文允许为空但应明确提示。
- 自动生成创建时间和更新时间。
- 保存成功后再提示成功，不能只更新前端假数据。
- 搜索索引更新失败时允许重建，不影响原始资料保存。

### 6.2 AI 摘要生成

输入：资料标题、正文、用户指定的摘要长度。

输出：

```
{
  "summary": "资料核心内容概述",
  "keyPoints": [
    "重点一",
    "重点二"
  ],
  "keywords": [
    "关键词一",
    "关键词二"
  ]
}
```

处理要求：

1. 检查正文是否为空。
2. 对过长文本按段落切分，设置合理的输入长度限制。
3. 通过统一 AI 接口请求模型。
4. 校验返回结构；异常格式应重试解析或提示错误。
5. 用户确认后再将结果写回资料，避免覆盖原始正文。

### 6.3 基于资料的 AI 问答

这是产品最重要的差异化功能之一。

用户输入问题后，系统先检索本地资料，再把相关内容和问题提交给模型，要求模型根据资料作答。

```
用户问题
  ↓
关键词提取与全文检索
  ↓
匹配相关资料和原文片段
  ↓
构造受长度限制的上下文
  ↓
AI 生成答案和来源引用
  ↓
展示答案、资料标题及引用片段
```

返回结构示例：

```
{
  "answer": "根据保存的会议记录，本周需要完成接口联调。",
  "sources": [
    {
      "documentId": "doc-001",
      "title": "项目周会记录",
      "excerpt": "本周五前完成接口联调并提交测试结果。"
    }
  ],
  "confidence": "medium"
}
```

这里的 `confidence` 只能作为模型或规则给出的提示，不应宣称是经过科学校准的概率。

问答规则：

- 优先引用真实存在的资料 ID 和原文片段。
- 没有检索到足够证据时，明确回答「现有资料中没有找到足够依据」。
- 不得把模型自行生成的内容伪装成原文引用。
- 来源引用可点击打开对应资料。
- MVP 使用关键词检索即可，不要求首版搭建向量数据库。

### 6.4 从资料中提取任务

输入：会议记录、工作总结、学习计划等文本。

输出示例：

```
{
  "tasks": [
    {
      "title": "完成接口联调",
      "description": "根据会议记录完成接口联调并验证结果",
      "dueDate": null,
      "priority": "high",
      "evidence": "本周五前完成接口联调"
    }
  ]
}
```

业务规则：

- AI 只提取文本中明确存在的任务。
- 未明确的日期不得擅自推断为具体日期。
- 提取结果先预览，用户确认后再写入任务表。
- 保存的任务应关联原始资料。
- 任务标题为空或重复时，提示用户修正或确认。

### 6.5 学习卡片生成

从资料中生成问题与答案：

```
{
  "cards": [
    {
      "question": "什么是数据库索引？",
      "answer": "数据库索引是帮助数据库更快定位数据的数据结构。"
    }
  ]
}
```

用户可以翻面查看答案，并标记：

- 不熟悉：稍后重新复习。
- 基本掌握：进入常规复习。
- 已掌握：降低复习频率。

首版只需要实现简单复习间隔，不必急于开发复杂的间隔重复算法。

## 七、AI 服务接口设计

### 7.1 统一 Provider

禁止在页面组件中直接散落模型 API 请求。

```
interface AIProvider {
  summarize(input: {
    title: string;
    content: string;
  }): Promise<SummaryResult>;

  answerQuestion(input: {
    question: string;
    contexts: SourceContext[];
  }): Promise<AnswerResult>;

  extractTasks(input: {
    content: string;
  }): Promise<ExtractedTask[]>;

  generateFlashcards(input: {
    content: string;
    count: number;
  }): Promise<FlashcardDraft[]>;
}
```

至少实现两种 Provider：

- `MockAIProvider`：使用确定性的示例数据或简单规则，确保没有 API Key 时仍能演示产品流程。
- `OpenAICompatibleProvider`：调用后端代理，通过配置适配兼容 OpenAI API 的模型服务。

重要安全要求： 正式发布时，禁止将真实模型 API Key 写入前端代码、公开环境变量或浏览器存储。若接入真实模型，应通过后端代理保存密钥，并限制请求大小、调用频率和超时。

### 7.2 后端接口（启用 FastAPI 时）

| 方法   | 路径                   | 功能     |
| ---- | -------------------- | ------ |
| POST | `/api/ai/summary`    | 生成摘要   |
| POST | `/api/ai/qa`         | 基于资料问答 |
| POST | `/api/ai/tasks`      | 提取行动项  |
| POST | `/api/ai/flashcards` | 生成学习卡片 |
| GET  | `/api/health`        | 健康检查   |

统一错误格式：

```
{
  "code": "AI_PROVIDER_ERROR",
  "message": "AI 服务暂时不可用，请稍后重试。",
  "requestId": "req-example"
}
```

后端必须完成输入校验、超时处理、异常日志脱敏和调用限流。不要记录用户完整资料正文或密钥。

## 八、全文搜索与文件导入

### 8.1 全文搜索

首版采用浏览器本地检索：

1. 标题匹配优先于正文匹配。
2. 支持标签、分类和收藏状态筛选。
3. 搜索结果显示命中的标题与上下文片段。
4. 对中文内容采用合适的分词或字符 n-gram 策略，不能只依赖英文空格分词。
5. 删除或编辑资料后同步更新索引。
6. 大型资料库应采用分页或虚拟滚动，避免一次性渲染全部内容。

### 8.2 文件导入

首版支持：

- `.txt`：直接读取文本。
- `.md`：读取 Markdown 原文。
- `.pdf`：使用 PDF.js 提取可选取的文本内容。

暂不支持复杂扫描件 OCR、加密 PDF 和 Office 文件全格式解析。

导入流程：

1. 选择文件。
2. 校验格式和大小。
3. 解析文本并显示预览。
4. 用户填写或确认标题、分类、标签。
5. 用户确认导入。
6. 保存至 IndexedDB 并更新索引。
7. 显示成功或失败的文件清单。

建议首版设置单文件 10 MB 的可配置上限，并对 PDF 页数和提取文本长度进行限制。解析失败时给出可理解的错误原因。

## 九、隐私、安全与可靠性

由于产品处理的是个人文档，隐私是实际使用价值的一部分。

必须满足：

- 默认本地保存，明确说明数据保存位置。
- 未经用户明确操作，不自动把整份资料发送给 AI。
- 调用 AI 前告知用户将发送哪些内容。
- 提供导出备份、导入恢复和清除本地数据功能。
- 不在日志中记录 API Key、敏感资料正文或不必要的个人信息。
- 对 AI 返回结果进行结构校验，不能直接信任模型生成的 JSON。
- 防范恶意文件、超大输入和异常响应。
- 外部链接不得自动执行或作为可信指令。
- 所有用户输入均按普通文本安全渲染，禁止直接执行资料中的 HTML 或脚本。
- 对 AI 输出中的指令进行隔离：资料内容只能作为待分析数据，不能覆盖系统规则或触发未经用户确认的操作。

另外，浏览器本地存储不等于加密保险箱。敏感资料仍可能受到设备被共享、浏览器环境被攻击等风险影响，产品不能承诺绝对安全。
